Without the agent — today

1Exception fires — lands in the logistics specialist's queue
2Specialist reads the case — opens the ticket, finds the tracking number, looks up the carrier portal
3Contacts the carrier — calls or emails, waits for a status update (minutes to hours)
4Drafts a customer message — manually writes a delay or correction notice
5Fills a claim form — if package is damaged or lost, fills out a separate damage claim portal
6Creates an escalation ticket — manually assigns severity and routes to customs, ops, or investigation team
7Tracks follow-up — monitors for closure, updates the record

15–40 min per case · inconsistent across specialists · doesn't scale

With the agent — now

1Webhook fires — POST /case with the full exception JSON. Worker returns 202 immediately.
2ExceptionDO initializes — Durable Object creates an isolated state machine for this case. Status: pending → processing.
3LLM reads the case — static system prompt + filtered tool schemas + case JSON sent to Subconscious. Model reasons through exception type and selects tools.
4Tools execute in the Worker — contact_carrier, notify_customer, file_claim, escalate — real HTTP calls, real ntfy.sh push notifications.
5LLM sees results, resolves — tool outputs fed back; model writes a plain-language resolution summary. Status: resolved.
6Audit trail written to R2 — every tool call, argument, result, and LLM response stored as structured JSON for compliance review.

~2–3s end-to-end · same resolution path every time · scales to any volume

How the LLM reasons through a case

1
Static system prompt → prefix cache hit
The system prompt is never interpolated — it's the same string every call for the same exception type. Subconscious server-side prefix caching kicks in: the prompt + tool schemas are already tokenized and cached, so only the new case JSON is billed as input tokens on subsequent calls.
// loop.ts — never interpolated const SYSTEM_PROMPT = `You are a Wayfair logistics exception-resolution agent...`;
2
Tool filtering — LLM only sees what's relevant
Before each call, the tool schema list is filtered to only the 2–4 tools that apply to this exception type. A delayed_shipment case never sees void_label or file_claim. This keeps the context window well under the 8192-token limit and prevents the model from hallucinating irrelevant tool calls.
CASE_TYPE_TOOLS = { delayed_shipment: ["contact_carrier", "notify_customer", "escalate"], delivery_dispute: ["file_claim", "escalate", "notify_customer"], duplicate_shipment: ["void_label", "notify_customer"], ... }
3
Selective thinking — deep reasoning only when it matters
Simple cases (delayed shipment, address not found) run with enable_thinking: false — fast and cheap. Complex cases that require multi-factor judgment — delivery_dispute, customs_hold, damaged_package — get enable_thinking: true. The model internally reasons through claim type, order value thresholds, and escalation severity before emitting its first tool call.
THINKING_CASE_TYPES = new Set([ "delivery_dispute", // → should we file dispute or loss claim? "customs_hold", // → which broker team? what delay notice? "damaged_package", // → refund vs reschedule depends on order_value_usd ]);
4
Native tool_calls — not ReAct JSON parsing
The agent uses OpenAI-compatible tool_calls (not a custom ReAct JSON format). The LLM returns finish_reason: "tool_calls" with a structured function call array. The Worker executes each tool, appends results as role: "tool" messages, and loops. No regex, no JSON parsing errors, no prompt engineering to force JSON shape.
// LLM returns: { finish_reason: "tool_calls", message: { tool_calls: [ { function: { name: "contact_carrier", arguments: '{"tracking_number":"1Z999..."}' } }, { function: { name: "notify_customer", arguments: '{"type":"delay_notice",...}' } } ]}} // Worker executes both, appends tool results, calls LLM again
5
Loop until stop — up to 8 iterations with token accounting
The loop continues until the LLM returns finish_reason: "stop" or hits the 8-iteration cap. Prompt + completion tokens are accumulated across all iterations and stored on the case state. Token budgets are per-case-type (400–900) to avoid over-generating on simple cases.
MAX_TOKENS_BY_TYPE = { duplicate_shipment: 400, // void one label, done delayed_shipment: 600, // contact + notify damaged_package: 900, // claim + decision + reschedule/refund }
6
Durable Object — idempotent state machine per case
Each exception gets its own Durable Object with SQLite-backed state. The DO enforces the pending → processing → resolved/failed state machine — a second webhook for the same case ID hits the existing DO and returns the current state immediately (no double-processing). The full audit trail is stored in DO state and flushed to R2 on resolution.

What each tool does

Tool What it does Used for
contact_carrier Gets current shipment status from the carrier API delayed_shipment, return_not_received
notify_customer Sends push notification to customer channel (ntfy.sh) delay_notice, address_correction, refund_issued
escalate Creates ops ticket + fires priority push to ops channel customs_hold, carrier_api_failure, disputes
file_claim Submits damage or dispute claim with evidence URLs damaged_package, delivery_dispute
void_label Cancels a duplicate shipping label duplicate_shipment
refund Issues full or partial refund to the customer damaged_package (when reschedule not viable)
reschedule Books a new delivery window damaged_package (when replacement is preferred)
